# BrewMaster

A recipe workbench with two visibly distinct layers: deterministic brewing calculations and subjective flavor estimates. Built in six committed stages.

## Run

Node 22.13+ required; Node 24+ recommended (Node's built-in SQLite avoids native dependency compilation).

```sh
npm install && npm run dev
```

Open http://127.0.0.1:5173. React/TypeScript/Vite + Tailwind frontend, Express/TypeScript API, SQLite in `.runtime/brew.sqlite`. No accounts or external AI services. Local development stores data on this machine; the hosted app has private browser workspaces and an optional public Community collection. `npm test` runs engine and API tests; `npm run build` checks TypeScript and builds the frontend. `npm start` serves the built app on port 3001.

## Optional sharing and private workspaces

No account is required. A random 256-bit ownership token is kept in an HttpOnly, SameSite=Lax cookie; the database stores only its SHA-256 hash alongside each record. Production uses a Secure, host-only `__Host-` cookie with no Domain attribute. The cookie lasts one year. `src/api.ts` establishes it before concurrent initial reads or early saves. Workspace API responses are not cacheable, do not return ownership secrets, and distinguish record visibility from edit ownership. This is anonymous browser ownership, not account synchronization or recovery: another browser/device has a separate workspace, and clearing/losing site data or expiry loses private access. Export JSON backups before clearing site data. Public copies do not grant editing rights to the original.

New rows default to `private`. Saving a copy makes a new private recipe even when its source was public. Sharing explicitly publishes ingredients, process parameters, description and all recipe/process/additive notes, with a `?recipe=<id>` link. **Make private** removes that recipe from other visitors' API results and makes its link unavailable to them. Copies and exports already held by someone else cannot be recalled. New brew logs, recipe snapshots, personal ingredient evidence and tasting notes remain private even if the associated recipe is public. Recipe JSON and BeerXML describe the brew, not its access rights; copies and imports do not inherit public visibility.

The SQLite startup migration preserves pre-existing intentionally public recipes and brew logs. These have no ownership token and appear as read-only Community recipes or labeled previously shared logs; a visitor cannot claim, modify or delete them. They are not silently made private for the first person to visit, and legacy public logs are excluded from personal calibration. Their underlying records are retained. Fresh schema creation includes ownership and visibility columns; existing SQLite files receive additive column/index migrations.

## Architecture decision

A local Node API keeps a durable SQLite database independent of browser storage eviction and makes future Postgres migration straightforward. `server/schema.sql` uses portable SQL, UUID text keys and JSON encoded as TEXT. Postgres requires a new connection/query adapter (`?` to `$n`, transaction API) rather than schema redesign; it is not a connection-string-only switch. The engine under `src/engine` has no React, database or network dependencies. Canonical recipe units are kg/g/L/°C; US display converts at the UI boundary.

## Data sourcing

`data/*.json` is the reviewable source of truth. Numeric records are imported from Brewtarget's brewing reference tables (links on every row), not claimed as verified current manufacturer certificates. Most hop entries publish typical points rather than true ranges: `[x,x]` explicitly means a reference point. Unknown oil components, POF, diastaticus, alcohol tolerances and diastatic power are `null`, never fabricated zeros. Check the lot analysis before brewing. Original upstream descriptions are discarded. Flavor associations are editorial interpretations of reference associations; intensities and process responses are model estimates, not sourced measurements. Generic malt/body labels are low confidence heuristics. All descriptor notes are newly written. Numeric legacy style ranges are included without guideline prose and are labeled as legacy, not current BJCP guidance.

`npm run seed` regenerates reviewable JSON from upstream reference files (downloads when absent). It should only be run deliberately: it replaces manual edits. The API reseeds catalog tables from JSON at startup; recipes and brew logs survive. Source and confidence travel with every descriptor. Unknown specs remain visible.

## Adding ingredients and vocabulary

Add an objective record to `malts.json`, `hops.json`, or `yeasts.json`, using a unique stable ID and source URL/title/date. Add subjective records only to `descriptors.json`, with controlled descriptor IDs, confidence and structured context (use, min/max grist %, min/max temperature). Multiple conflicting records are allowed. Add vocabulary entries to `vocabulary.json` (`parent` groups the wheel, `axis` promotes to target sliders). No engine changes are required. Restart the API after editing seed files.

## Stages

1. Data model, normalized schema, sourced numeric seed data and separate controlled descriptors.
2. Pure calculation engine and reference-value tests.
3. Live recipe editor, units, persistence and export.
4. Contextual flavor prediction and source explanations.
5. Constrained recipe solver with ranked candidates and tradeoffs.
6. Brew logs, tasting feedback and opt-in calibration.

## Deterministic calculations and explicit approximations

- OG = 1 + Σ(lb × PPG × efficiency fraction) / gallons / 1000. Extract and sugars use 100%. Malt EBC ≈ 2.65 × °Lovibond − 1.2 (clamped at zero); this is distinct from beer EBC = 1.97 × SRM. Seed PPG = extract % × 0.46214 (46.214 PPG sucrose basis).
- FG = OG − (OG − 1) × apparent attenuation. Baseline uses midpoint of the yeast range. **Heuristic:** each °C below 65°C adds 0.75 percentage points of attenuation; each °C above subtracts 0.75, clamped to 40–95%. Each fermentable's gravity points are weighted separately: crystal/caramel uses 65% of baseline attenuation; lactose 0%; simple sugars 100%. These are rough planning assumptions, not laboratory fermentability analyses. Mash time does not change attenuation in this model.
- ABV standard = (OG − FG) × 131.25. Default accurate formula = (76.08 × (OG − FG)/(1.775 − OG)) × (FG/0.794). Both remain gravity-based estimates.
- Tinseth U = 1.65 × 0.000125^(boilSG − 1) × (1 − exp(−0.04t))/4.15. IBU = U × AA fraction × oz × 7490 / gal. Boil SG is the mean of pre/post-boil gravity (approximation). Whirlpool uses its entered duration times a configurable 0–1 multiplier (default .15); this does not model temperature decay. Dry hop IBU = 0 (no isomerized-alpha contribution; perceived bitterness can still change).
- Morey SRM = 1.4922 × MCU^0.6859; MCU = Σ(lb × °L)/gal. EBC = SRM × 1.97. Screen swatch is an illustrative exponential RGB approximation, not calibrated photometry.
- BU:GU = IBU / ((OG−1)×1000), zero for zero gravity points.
- Degrees Plato = −616.868 + 1111.14 SG − 630.272 SG² + 135.997 SG³. ABW = 76.08(OG−FG)/(1.775−OG); real extract = .1808 × OG Plato + .8192 × FG Plato. Calories per 12 US fl oz = [6.9 ABW + 4(real extract − .1)] × FG × 3.55; 330mL scales by 330/354.88235. Approximate; not nutritional labeling.
- Batch volume means **post-boil kettle volume**, before entered transfer loss. Pre-boil L = batch L + boil-off L/h × boil hours. Transfer loss reduces fermenter volume, not kettle concentration. Pre-boil SG conserves gravity points. Does not model grain absorption, shrinkage or sparge water.
- Pitch cells (billions) = 0.75 (ale) or 1.5 (lager) × volume L × degrees Plato × pitch multiplier. No viability or starter-growth model.
- Scaling multiplies all masses by new/old volume and mash grains additionally by old/new efficiency. Extract/sugars keep full yield. It preserves OG, color approximately changes when efficiency changes; hop timing and boil-off rate stay equipment settings.

Reference formula names: Tinseth hop utilization, Morey color, standard apparent attenuation/ABV and real-extract calorie estimation. Formula constants are recorded here so each can be independently checked; high gravity and extreme color recipes exceed their practical accuracy.

## Recipe editor and exchange

Every ingredient amount, hop alpha acid, addition timing/use, yeast, temperature and equipment setting is editable. Numbers update immediately; save writes explicitly to SQLite. Unsaved ingredient edits and beer goals are backed up in browser storage; save to keep a recipe in the Recipe Book. US/metric preference persists in localStorage; recipe data does not depend on it. JSON import validates bounds and known ingredient IDs. BeerXML 1.0 import/export supports one recipe, one known yeast and single-infusion mash; unsupported ingredients, mash steps and hop uses are rejected so the user can resolve them rather than silently losing data. Catalog matching uses Brew Designer IDs or exact ingredient names. BeerXML volumes are L, masses kg and temperatures °C. Optional BD_* fields preserve transfer loss, whirlpool factor, pitch multiplier and style selection on round trip. Multi-strain fermentations, detailed water chemistry and complex mash profiles are outside this version's scope. Known optional additives are supported as scheduled BeerXML miscellaneous entries, with the modeling limitations documented below. Print exports the current recipe and calculated brew-day numbers.

## Flavor model (subjective)

Every score is an estimate on a 0–5 scale, never a measurement. Context is matched before consensus: addition use, min/max grist percentage, min/max fermentation °C. Confidence weights low/.45, medium/.75, high/1 multiply source weights manufacturer/1.1, literature/1, community/.8 and user/adjustable 1–3. Conflicting records are retained, with their weighted mean used in prediction. Context overlap is intentionally included; it does not select only one source.

- Malt raw intensity = consensus × sqrt(grist fraction), with ×3 for non-base ingredients. Chocolate contribution is halved above 10% roasted grist; burnt descriptors activate at 10%. These are editorial threshold models.
- Hop raw intensity = consensus × timing × [1−exp(−g/L÷3)] × sqrt(total oil÷1.5). Timing is 1 dry hop, .85 whirlpool, exp(−minutes/18) boil. Unknown oil defaults to 1.5 mL/100g and is disclosed in its explanation. Oil chemistry is not a full aroma or biotransformation model.
- Yeast esters use multiplier (.6+.9×warm-position) × (1/pitch multiplier)^.25; phenols .85+.3×warm-position. Warm-position is 0–1 within the strain temperature range. Clean/other descriptors use 1. Fermentation oxygen, pressure and hop-creep are not modeled.
- Sensory scores saturate as 5×[1−exp(−sum raw/5)]. Ingredient contribution totals are rescaled by the same saturation, so they add exactly to the displayed score.
- Structural axes replace descriptor sums: body = clamp((FG−1)×180+(mash°C−65)×.12); sweetness = clamp((FG−1)×140−BU:GU×.4); dryness = clamp((attenuation%−50)/10); bitterness = clamp(BU:GU×3.3); carbonation = clamp(volumes/3.5×5); astringency = clamp(roast fraction×15). All clamps use 0–5. These are heuristic perceptions inferred from recipe properties. Each has a process explanation instead of invented ingredient evidence.

The library exposes all records and weighted context previews. Hop Aroma/Flavor/Bittering/Dry hopping roles overlap and are editorial suitability filters, separate from analytical hop purpose. Malts filter by grist role, yeasts by family/form. Yeast tolerance filtering excludes unknowns only when a minimum is active. Potential ABV filtering uses entered OG and midpoint yeast attenuation with the accurate ABV formula; it is not a promise that a yeast produces a particular ABV. Full guides are newly written using record-specific numbers and clearly labeled process heuristics. Hop substitutions score 65% descriptor cosine similarity, 25% mean shared-oil closeness, 10% alpha similarity; missing data weakens the evidence.

Navigation preserves the editor and library components, their controls and each screen's scroll position. Recipe drafts are backed up to browser localStorage immediately after each edit, while explicit Save writes the durable SQLite copy. A browser backup is not a cross-device sync service. The mobile navigation stays available while scrolling on brew day.

## Solver

The solver runs in a dedicated browser worker and uses seeded deterministic gradient-free search. It ranks ingredients by desired descriptor overlap, filters excluded/on-hand ingredients, yeast form and alcohol tolerance, then explores 18 combinations of shortlisted base malt (6), specialty (8), hops (8) and yeast (6). Seventy local coordinate moves per start vary specialty fraction, mash/fermentation temperature, aroma/dry-hop amounts and late-boil versus whirlpool use. A gravity correction iteratively approaches target ABV and a per-gram Tinseth calculation sets remaining kettle bitterness. This is a bounded local search, not a global optimum or exhaustive recipe enumeration; unknown sensory evidence cannot guarantee the absence of a flavor.

Objective: flavor weight × mean squared 0–5 axis distance + numeric weight × squared normalized ABV(.5%)/IBU(10)/SRM(3) distance + style weight × distance outside style numeric ranges (OG .005, FG .003, ABV .5%, IBU 10, SRM 3). Optional user OG/FG ranges add the same normalized distance. Must include means score ≥1 (penalty ×8 below); avoid means ≤.3 (penalty ×10 above). These are soft sensory constraints and conflicts are explicitly reported. Ingredient exclusions, allowlist and yeast form are hard constraints; candidates over reference max grist percentages are discarded. A strict on-hand allowlist needs all required ingredient kinds. Quantities on hand are not tracked. Economy is a disclosed budget proxy (dry yeast and total hops ≤4 g/L), not a priced cost optimization. No live prices are claimed. Results are the top three starts; limited inventories can make them very similar. Recipe name, ingredient rationale, scores and numeric/sensory conflicts are exposed for review. Changing targets marks existing results stale and cancels an in-flight search.

## Brew log, tasting and personalization

Logs store the complete recipe and prediction snapshot at save time, measured OG/FG/post-boil volume/fermentation temperature, notes and only the tasting axes explicitly rated. Measurement fields begin at predicted values for convenience and must be replaced with real readings. Old predictions are never recomputed as you edit a recipe. Export all logs as JSON for backup.

Whole-beer tasting ratings show residuals (actual minus predicted); they do **not** automatically become assertions about individual ingredients. The brewer can explicitly attribute a controlled descriptor to one ingredient, at a chosen confidence. Those notes persist in the separate `flavor_descriptors` table as source_type=user. Usage context is hop use, fermentation ±1°C, or grist fraction ±2 percentage points. Personal notes remain visible in the library; including them in recipe/solver predictions is opt-in, with adjustable source weight 1–3. This learns associations, not validated causality.

Efficiency calibration solves E = (actual gravity points × actual post-boil gallons − fixed extract/sugar points) / mash potential points. Values outside 20–100% are excluded. Valid brews are averaged; applying the estimate keeps ingredient amounts fixed and changes recipe efficiency explicitly. Per-yeast calibration first inverts the model's sugar/lactose/crystal weighting and mash-temperature offset from observed attenuation, then averages valid 40–95% baseline estimates for that yeast. This avoids applying those heuristics twice. Per-yeast calibration is separately opt-in for the editor; solver uses catalog attenuation and personal descriptors, not the strain calibration, so candidate predictions should be checked in the editor. No automatic accuracy guarantee: sampling bias, measurement errors and process changes affect calibration. Preferences persist locally; stored user notes and measurements live in SQLite.

Manufacturer corrections live in `data/overrides.json`, applied after reference import. The US-05 attenuation, temperature, tolerance and POF fields were checked against [Fermentis technical specifications](https://fermentis.com/en/product/safale-us-05/); unverified remaining strain fields retain reference provenance.

Upstream Brewtarget numeric tables are pinned to commit `531d5e7523f9e72a0054349bd5b14aa1c7bf16ad`; the reference blobs match `32f20aa8f9fcf689de138d4c33cb5ac5797090a4` (XML) and `58a031c568afa19f4999b0d1c23b64b1a038ff46` (BeerJSON). Three legacy malt records lack a usable max-in-batch value; their permissive 100% model cap is not manufacturer usage advice.

## Suggested hops and malts

The recipe editor's **Suggested hops / Suggested malts** panels provide a hand-curated shortlist in `data/suggestions.json`. “For this recipe” prioritizes an editorial style-family match and ingredients not yet present; “Popular starting points” keeps the curated order. Neither mode is a measured popularity, sales or sensory ranking. The library can filter to the same beginner shortlist. Existing acid, color and potential specs stay separate from the suggestion's subjective rationale and its source link.

Hop suggestions filter bittering, late flavor/aroma and dry hopping. Trial doses are respectively 0.5, 1 and 1.5 g/L; bittering time is min(60, recipe boil minutes), whirlpool 20 minutes, dry hop 3 days. These are editable trial heuristics, not optimized IBU targets. Bittering suggestions require a positive boil duration. Each card previews deterministic changes in ABV percentage points, IBU and SRM before applying. Adding a hop preserves previous additions.

Malt suggestions filter base, malt character, caramel, body and roast roles. A base swap replaces the first base malt and adjusts mass by old PPG/new PPG to retain that grain's gravity contribution. Other grains remain fixed. A new specialty's mass = existing total × desired final grist fraction/(1−fraction), bounded by the catalog max share. Duplicate malts are directed to the existing editor row. With an empty grist, add a base first (initial base trial 0.2 kg/L). Suggestions never silently remove an existing recipe to install a full preset. Actual flavor impact is uncertain and should be evaluated on the live profile.

An applied suggestion can be undone from its panel while the recipe still matches that suggestion’s result. Later manual edits or other additions disable that undo so it cannot overwrite newer work.

The Recipe Book opens on **Style collection**, with **All recipes**, **My recipes** saved to SQLite, and browser-backed **Drafts** also available. Search matches names, breweries, styles, ingredients, tags, descriptions and notes; filters select collection, brewery, style or source type. Each card displays current catalog-based calculated ABV/IBU/SRM, with full ingredients, process, notes and exports available under View recipe. These card calculations use reference yeast attenuation, not optional personal calibration, so check a loaded recipe in the editor when calibration is enabled.

`data/recipes.json` includes 19 entries: seven original educational formulations, three brewery-recipe adaptations, one published-clone adaptation and eight independent house clones. The [Sierra Nevada Pale Ale adaptation](https://sierranevada.com/blog/our-beer/pale-ale-homebrew-recipe) retains 92/8 grain percentages and the published Cascade masses/timings; the source does not give a total grain weight in its ingredient list, so this template assumes 4.5kg and documents efficiency, catalog mapping, volume and equipment assumptions. The source's mash-out remains in notes because the engine supports one mash rest. Descriptions and instructions are newly written, and no brewery validation is claimed. Original starter recipes are not presented as established commercial recipes or successful brew trials.

Using a starter always creates a new ID. Saved recipes can be reopened, duplicated or saved as a copy. Saving in the editor adds/updates My recipes; a copy does not overwrite the original. Description, notes, tags and source attribution persist in SQLite's existing recipe document and JSON, and round-trip through NOTES/BD_* BeerXML fields. Per-recipe drafts are kept in localStorage (`brew-drafts`) so opening another recipe retains earlier work. A saved recipe with local edits appears once, marked Unsaved edits, and opens its draft. Drafts remain browser-local; Save is the durable database step. No existing saved recipes are replaced when the starter collection changes.

The Recipe Book includes the original 12 craft interpretations and seven original starters, plus 70 style-coverage templates. Brewery and source-type filters distinguish (1) brewery-provided recipes adapted to the app, (2) published third-party clone adaptations, and (3) independently authored house approximations based on official commercial beer descriptions. A commercial product page is never presented as a disclosed brewing formula. Existing saved recipes and browser drafts are untouched; recipe origin metadata survives copies and exports.

The collection covers Sierra Nevada Pale Ale, Torpedo and Celebration; Bell’s Two Hearted; Stone Ruination; Founders All Day IPA; Deschutes Fresh Squeezed; New Belgium Fat Tire **Classic Amber**; Dogfish Head 60 Minute IPA; Ballast Point Sculpin; Lagunitas IPA; and Left Hand Milk Stout. ### Recipe coverage by beer style

The shipped book contains **89 recipes covering all 80 beer-style entries** in the app's legacy numeric catalog. **Style collection** shows all built-ins; **Craft & clones** shows the 75 brewery-associated entries. Expand **Browse by style** to see coverage and jump directly to a style. Coverage uses shipped recipes, independent of user saves, drafts and search filters. `data/non-beer-styles.json` explicitly excludes the 18 cider, perry, mead and honey-hybrid entries from the beer requirement. A newly added beer style counts as missing until a recipe is added; the coverage test catches gaps. This is complete coverage of this catalog, not a claim to include every modern or regional style worldwide.

The 70 additions comprise 63 independent brewery-inspired interpretations and seven original house starters. Their commercial names and historical style associations were checked against the [BJCP 2008 commercial examples](https://www.bjcp.org/wp-content/uploads/2019/08/2008_stylebook.pdf), with Baltic Porter verified against its [category page](https://legacy.bjcp.org/2008styles/style12.php) after a PDF extraction error. `data/style-recipe-references.json` records selected names and category codes; links on each recipe lead to the corresponding historical reference. These are historical associations, not claims of present brewery ownership, availability, or current product specifications. Known craft examples are favored; traditional breweries cover some regional styles. No guideline descriptions or brewery marketing prose are copied.

**These are authored homebrew interpretations, not disclosed brewery formulas.** Each style plan in `scripts/expand-style-recipes.ts` explicitly chooses its grist, yeast, fermentation, mash, house ABV/IBU targets and process instructions. The existing deterministic engine scales total grist by bisection to the house ABV target and scales kettle hop weights linearly to the house IBU target. Published commercial numbers are not invented or inferred from those targets. The script regenerates only `style-*` templates in `data/recipes.json`; review and commit that JSON after generation (`npx tsx scripts/expand-style-recipes.ts`). Existing built-in recipes and user SQLite data are not rewritten. Flavor descriptions express intent and remain subjective.

Special-process cards explicitly label the calculated values as **base beer estimates**. Fruit, spices, oak, extended mixed-culture fermentation, aged blending and ice concentration appear as quantified instructions in brewing notes, because the current model cannot represent their full extract, attenuation, acidity, color, volume, carbonation or sensory effects. Eisbock is a base bock plus concentration instructions, and gueuze is a base wort plus a long-term blend plan; their card numbers are not finished-product predictions. Malt, hop, yeast, main mash and fermentation settings remain editable. Source and limitations survive copies and JSON/BeerXML exports through existing notes, tags and origin metadata.

The existing browser draft bank backs up edits as you type and retains them across screen changes and reloads. JSON exports preserve the structure. ### Recipe Book hop and flavor profiles

Every card lists its hop varieties, doses and addition uses/timings from the saved recipe, respecting the unit toggle. A separate subjective panel lists the four strongest non-structure flavor/aroma descriptors (scores ≥0.25/5), plus body, dryness and perceived bitterness. These are calculated by the existing context-aware consensus model, not copied brewery tasting notes or measurements. With insufficient descriptor evidence, the card says so rather than implying no flavor. **View recipe** opens the flavor radar and the same axis explanations, ingredient contributions, source badges and confidence used in the editor. Special-process limitations still apply: fruit, spice, wood, mixed cultures and concentration can change the finished profile beyond the model. Recipe Book uses the catalog's consensus layer without personal attenuation calibration, matching its numeric cards.

### Design parameters and live ingredient recommendations

In **Design**, change style, target ABV, IBU, SRM, batch volume or efficiency, then set flavor targets. **Hop flavor direction** offers editable editorial tropical/citrus, pine/resin, floral/herbal/spicy and earthy/woody starting points in `data/hop-flavor-directions.json`; choosing one replaces only the hop-family targets. Individual hop descriptors are adjustable under **Fine-tune individual hop flavors**. **Use style flavor starting point** explicitly replaces sensory targets with model estimates from a representative Recipe Book template. Choosing a style manually preserves all numeric and sensory targets and selected hops, base malt and yeast, and turns off automatic style matching. Suggested ingredient rankings may update, but changing the style never applies suggestions or rewrites a recipe.

**Ingredient matches** updates immediately, with separate reference specs and subjective reasons/evidence. It shows the style's example grist, plus searchable malt, hop and yeast shortlists. Hop usage selects the descriptor context (late boil, whirlpool or dry hop); the bittering role additionally favors alpha-acid efficiency. The optional evidence filter retains hops with intensity ≥0.5/5 for at least one positively targeted hop descriptor. If no hop targets are positive it does not pretend to narrow the list. Exclusions and strict on-hand allowlists apply to all ingredient kinds. Yeast form, budget proxy and known alcohol tolerance also filter strains; unknown tolerance stays visible with a verification note. Actual beer alcohol depends on fermentable wort and attenuation, not yeast choice alone.

Ranking is an editorial heuristic, not an objective suitability percentage. Its base score sums `target intensity × contextual consensus intensity / 5`, adds 5 for a must-include descriptor and subtracts `8 × intensity` for an avoided descriptor. A match in the book's style templates adds 6 (14 for yeast), the existing curated family shortlist adds 3, specialty malt color distance subtracts `0.03 × abs(°L − max(2, 3 × target SRM))`, and a yeast matching the broad ale/lager direction adds 5. Hops gain up to 12 for the share of desired hop-axis weight with descriptor evidence, 4 for evidence on a strongest target axis, and in bittering mode `0.7 × midpoint alpha acid %`. Missing evidence is disclosed, not interpreted as a measured absence. These scores rank candidates; recipe-level optimization still uses the established numeric/style/flavor objective and grist caps.

`data/style-ingredient-profiles.json` contains the editorial style priors and representative grists derived from the built-in Recipe Book. `scripts/expand-style-recipes.ts` refreshes that file along with recipe seeds; it is not a sales/popularity dataset or brewery-validated recommendation. Ingredient/source evidence stays in the original catalog and descriptor records. The displayed grist is a starting example, not the exact formula the optimizer will return.

Optional **Choose hop** selections restrict the generated hop pool, **Choose base malt** fixes the base, and **Choose yeast** fixes the strain. Choices do not override inventory, form, tolerance, budget or grist limits; contradictory selections return an actionable infeasibility message. All chosen hop varieties are allowed, but the solver need not use every variety in every candidate. Changing targets marks prior results stale and cancels an active search. The solver now shares these candidate rankings, initializes timing/doses from the selected hop role, and reduces late hot-side additions when necessary to meet a low IBU target before calculating the kettle bittering dose. Dry hops remain zero IBU in the model.

From **Recipe Editor**, **Adjust targets & get ingredient suggestions** starts a new brief from the current recipe's calculated numbers, predicted sensory profile and equipment. The current recipe remains in the draft bank. Opening a result makes a new redesigned recipe retaining the user's name, description, general notes and process notes; amounts, ingredients and process settings may change. Old brewery-formula provenance is not automatically asserted for an independently generated redesign. All resulting parameters remain manually editable in the Recipe Editor.

### Optional additives and process aids

**Ingredient Library → Additives** provides 24 searchable guides grouped by category and suggested brewing stage: cocoa/cacao nibs, cocoa powder, oak chips/cubes, bourbon/rum, vanilla beans/extract, coffee/coffee liquid, coconut, cinnamon, coriander, orange peel, ginger, chili, raspberry/cherry/mango purée, Irish moss, Whirlfloc, gelatin, silica finings and Wyeast Beer Nutrient Blend. Each guide separates material identity and form from editorial usage suggestions and subjective sensory associations. Source links are on the cards. `data/additives.json` is the editable identity/usage catalog; `data/additive-descriptors.json` holds the separate low-confidence sensory layer using the controlled vocabulary. The SQLite ingredient table records `kind=additive`, `additive_specs` stores identity and labeled guidance, and descriptor rows use the existing `flavor_descriptors` table. These records are kept out of the current recipe flavor-score model until an extraction/dose model exists.

The cocoa/coconut guide references the [Phase Three brewer discussion](https://www.beerandbrewing.com/video-tip-phase-3-tip-2); oak and vanilla references identify supplier product forms, [fruit guidance](https://morebeer.com/blogs/articles/fruit-beer-flavor) describes addition practice, and [fining references](https://morebeer.com/collections/brewing-clarifiers) identify process roles. Spirit guidance cites a labeled AHA community discussion rather than a manufacturer formula. General spice and alternate extract examples use a broad supplier-category reference and disclose their editorial nature. Sample amounts and contact times are **house trial settings, not copied manufacturer dose ranges or validated flavor outcomes**. Product-specific finings, extracts and chili have a zero placeholder until the brewer chooses a label-based dose or bench trial. Zero-dose rows are flagged in the editor and prediction warnings. The Wyeast entry is the exception: it scales the explicitly verified [homebrew instruction of 2.2 g per 19 L, added 10–15 minutes before boil end](https://wyeastlab.com/product/wyeast-beer-nutrient-blend/); the manufacturer also lists a separate professional rate, which is not substituted for the homebrew instruction.

**Add to recipe** works from the library or **Recipe Editor → Optional additives → Browse additives**. Each optional recipe `additives` row stores a unique ID, catalog ingredient ID, canonical amount/unit (`g`, `mL`, or `item`), process stage, time/unit (minutes/hours/days), and free-text experiment notes. For boil-stage rows the time means time before the boil ends; elsewhere it is a planned contact/settling duration. Stage and duration remain editable for experiments. A count is not assumed to have a mass. US display converts grams to ounces and milliliters to **US fluid ounces**; it never conflates weight ounces with fluid ounces. Batch scaling multiplies additive amounts by volume ratio, without an efficiency correction; timings and notes stay fixed. Volume-scaled doses are planning heuristics and should still be checked against the product instructions and tasting trials.

Recipes, browser drafts, copies, SQLite saves and brew-log snapshots preserve the schedule and notes. Recipe Book detail views and printed brew sheets show it, and recipe search includes additive names and experiment notes. Redesigning a recipe carries its additive schedule into the new version, scaled only if volume changes. JSON and `BD_ADDITIVES` in BeerXML preserve exact fields. BeerXML also exports standard `MISCS/MISC` entries: mass is kg, liquid volume L, and time minutes. Counts cannot be converted to mass/volume without a product specification, so count-only entries use standard AMOUNT=0 plus readable count text in NOTES and exact `BD_AMOUNT`/`BD_UNIT` fields. Standard consumers must read the note for a tablet/bean count. Import resolves known additive names or IDs and preserves unlisted miscellaneous ingredients as named custom additions when their weight/volume unit is specified. Incompatible or missing units and unsupported stages return an error instead of silently dropping data.

**Model limitation:** additive doses are recorded, but their sugar, alcohol, dilution, color, flavor extraction, clarification and volume-loss effects are **not included** in OG/FG/ABV/IBU/SRM, calories, volumes or the flavor radar. Recipes with additions prominently label their numbers and radar as base-beer predictions. In particular, bourbon changes alcohol and volume, fruit can renew fermentation, and finings do not automatically improve the numeric flavor model. Add fermentable sugar or lactose through the existing fermentable grain bill when it must contribute to the current gravity model. Use the process notes and actual brew measurements to record observed results.


### Custom additive fill-in

Use **Add a custom additive · not listed?** in Ingredient Library → Additives or Recipe Editor → Optional additives. Enter a name, amount, weight/liquid/count unit, brewing stage, time and experiment notes. Custom rows use `ingredientId="custom"` with a required trimmed `customName` (1–200 characters); they remain explicitly user-defined rather than being inserted into the sourced global catalog. Their names are editable in the recipe schedule, and Recipe Book searches include them. Switching between weight, liquid and count resets the quantity to avoid inventing a density conversion; US displays use ounces and US fluid ounces as appropriate.

Custom fields persist in drafts, saves, copies, batch scaling, redesigns, print sheets and JSON/BeerXML exports. Named unlisted standard BeerXML MISC entries import as custom additions when `AMOUNT_IS_WEIGHT` or explicit BrewMaster unit fields make their physical unit clear. Counts need the existing extension fields; names, units, timings and notes are preserved without fake catalog references or numeric/sensory effects. Blank names, arbitrary unknown catalog IDs, negative amounts and unsupported units are rejected. No automatic flavor or ABV contribution is inferred for a custom entry.

### Automatic style matching and Design help

Design defaults to **Automatically match style to numeric targets**. Editing ABV, IBU, SRM, or optional OG/FG ranges immediately updates the closest legacy numeric style and its reference ranges. Matching changes only the selected style; it preserves entered targets, flavor sliders and ingredient choices. Turn automatic matching off to hold a style while experimenting, or select a style manually. Re-enabling automatic matching uses your current values without replacing them with style midpoints.

`src/engine/styleMatch.ts` ranks styles by summed squared distance outside their ranges, normalized by ABV 0.5 percentage points, IBU 10, SRM 3, OG 0.005 and FG 0.003. Optional gravity intervals use the gap between intervals; overlapping ranges have zero gap. Ties use normalized midpoint distance, then style ID for deterministic results. Mead/cider entries are excluded through `data/non-beer-styles.json`. Broad placeholder ranges are excluded: ABV upper bound must be positive and at most 20, IBU at most 150, SRM at most 80; maximum range widths are 8 ABV percentage points, 100 IBU and 40 SRM. All ranges must be finite and ordered. These are matching heuristics, not style definitions. The UI flags when even the closest style is outside your targets. Numeric similarity does not establish sensory similarity, fermentation method or style authenticity.

Design's information icons explain each control, including units, optimization constraints and sensory limitations. Hover or keyboard-focus an icon to read it; clicking pins the explanation, and Escape or an outside click dismisses it. Help text and vocabulary explanations live in `data/design-help.json`. Popups stay within the viewport for mobile use.

**Evaluate hop character for** has a visible explanation for the selected kettle bittering, late-boil flavor, whirlpool aroma or dry-hop context, plus an expandable comparison and clickable/hover help. `data/hop-character-help.json` contains original plain-language descriptions of when additions happen, typical sensory expectations and how the app uses the choice. Linked producer references cover [whole-leaf addition uses](https://www.yakimachief.com/products/whole-leaf-hops) and [whirlpool/fermentation guidance](https://www.yakimachief.com/products/veterans-blend). App-specific scoring and starting timings are identified as BrewMaster behavior; aroma expectations remain estimates. Whirlpool bitterness depends on the configured reduced-utilization approximation; dry hops contribute zero calculated IBU in this model, which does not promise zero perceived bitterness.

### Optional color target

Design starts with **Any color**. Enable **Set a color target** to enter SRM, or turn it off to leave color unconstrained; toggling it off and back on restores the last entered value. A redesign brief opened from an existing recipe initially includes its predicted color, which can also be disabled. Recipe color is still calculated and displayed as SRM/EBC with a swatch in all cases.

An omitted `Target.srm` is not zero or a hidden default. Style matching skips its SRM distance and midpoint comparison. The solver omits the numeric SRM penalty, style SRM penalty and SRM tradeoff messages. Specialty malt ranking omits its color-target distance; ingredient, flavor, alcohol and bitterness constraints still apply, and the selected style can still guide ingredient/process choices. Morey predictions and numeric style reference ranges remain available as information. Unit tests compare predictions with different SRM but identical other values to verify that optional color does not change their objective score.

### Starting water, ingredient amounts and bottles

Recipe Builder starts with **Water**, which scales the current recipe for total starting mash + sparge water. Editing starting water or grain absorption automatically updates every malt and hop amount and the post-boil batch size, preserving varieties, ratios, timing and efficiency. Yeast requirements and bottle yield update live, with no Apply button required. New manual drafts are initialized from five US gallons of starting water. Loading an older recipe without a water plan derives its required water from its batch, mash grains and boil-off. Once a water plan exists, manual grain-mass edits keep that water fixed and recalculate post-boil yield, without changing the entered grain mass or hop schedule. Invalid water budgets show an error and retain the last valid recipe. Save normally to keep scaled ingredient quantities. Water alone cannot specify the beer: the next step supplies beer goals and generates an editable starting recipe.

The pure `src/engine/waterPlan.ts` uses `post-boil L = (starting water L − boil-off L/h × boil minutes / 60) / (1 + mash grain kg / current batch L × absorption L/kg)`. This solves the circular relationship between scaled grain weight and absorption. Only mash-required grains absorb water. Default absorption 0.8 L/kg is an editable planning heuristic. Existing scaling scales transfer loss with batch size and keeps boil-off rate fixed. No cooling shrinkage, extra dead space, water from ingredients or top-up water is modeled. A minimum 0.5 L post-boil batch is required.

Packaging yield is `max(0, post-boil L − scaled kettle transfer loss − packaging loss)`. Default packaging loss is an editable 0.5 L. Full bottle count is the floor of yield divided by the selected bottle size (330, 500, 650, 750 mL or 12 US fl oz). This is a rough yield; it does not calculate priming sugar or carbonation safety. Water and absorption inputs support US and metric display.

Yeast requirement uses the existing ale/lager pitch calculation and recipe pitch multiplier. Dry yeast grams = required billion cells / assumed billion viable cells per gram; packets round up by the entered packet size. Liquid packs round up by viable cells per pack. The defaults (10 billion/g, 11.5 g dry packets, 100 billion per liquid pack) are editable planning assumptions, **not manufacturer specifications for the chosen strain**. Verify viability, product and storage with the supplier; liquid yeast may require a starter. Planner assumptions, bottle size and yeast dose are session estimates; the saved recipe retains its scaled ingredients, selected yeast strain and pitch multiplier, not a packaged yeast quantity.

### Yeast types, experimental cultures and alcohol guidance

The catalog contains **295 yeast entries**. Alphabetical type filters cover American, British/Irish and European ale, Belgian/saison, wheat, lager, kveik, high-gravity/super strains, conditioning, Brett/mixed culture, wine/cider/mead and baking yeast. These are overlapping editorial browsing groups in `data/yeast-families.json`, separate from objective strain specs. The editor's **Yeast type** filters its strain dropdown and keeps the current strain available; filtering alone never changes the recipe. The library's **Use this yeast in recipe** changes only the selected yeast and retains the working recipe and library position.

`data/yeasts-extra.json` adds Lalvin EC-1118, D47, 71B, K1-V1116, QA23 and RC212, Fleischmann's Active Dry and RapidRise, Red Star All-Natural Active Dry, and LalBrew Voss. `data/yeast-guides.json` holds original descriptive guidance separately from numeric specs. The seeded `yeasts.json` and `descriptors.json` remain fully reviewable; `scripts/seed.py` merges the extras, `vocabulary-extra.json` and `overrides.json` when regenerating. Baking entries identify real products but assert no supplier beer tolerance, attenuation or fermentation temperature. Wine/cider legacy attenuation figures are omitted because the reference does not establish performance in malt wort.

Alcohol tolerance is a strain/process limit, not the ABV a yeast automatically creates. The library estimates an **ABV interval at the entered OG** by applying the low and high reference apparent-attenuation endpoints to the documented FG and accurate ABV formulas, without recipe-specific mash/grist adjustments. ABV filters use interval overlap; setting an ABV filter excludes entries with unknown wort attenuation. Minimum alcohol-tolerance filtering separately excludes unknown tolerances. Name/code search prioritizes exact product codes such as WLP099 above references to that code in other descriptions.

Unknown attenuation and temperature are stored as `null`, never fabricated objective values. For a manually chosen culture with unknown malt-wort attenuation, the recipe engine uses an explicitly disclosed **75% house attenuation baseline**, followed by the existing mash/grist adjustments; optional personal calibration replaces that baseline. This is a placeholder for experimentation, not a validated prediction. A notice appears next to the recipe metrics as well as in model warnings. Unknown temperature produces no claimed manufacturer range; the sensory temperature multiplier uses a neutral midpoint. Automatic beer suggestions/solver candidates require known brewing specs and supported brewing types, so wine and baking options are deliberate manual choices. BeerXML omits unknown attenuation rather than exporting the placeholder as a strain spec.

Descriptor contexts now support `medium: beer | wine`, defaulting to beer for existing records. The wine library preview evaluates wine records in that context, while beer prediction excludes them. A manufacturer's wine aroma is not assumed to carry into a beer; the user's own beer tasting records can add contextual evidence. All 0–5 intensities remain editorial mappings, not measured supplier data. The generic **fruity ester** vocabulary entry avoids pretending that an unspecified fruity ester must mean a particular fruit.

New numeric records link to supplier product sheets. White Labs [WLP005](https://www.whitelabs.com/yeast-single?id=105&type=YEAST), [WLP090](https://www.whitelabs.com/yeast-single?id=144&type=YEAST), and [WLP099](https://www.whitelabs.com/yeast-single?id=146&type=YEAST) were refreshed from their current pages. WLP005/WLP090 list a 5–10% tolerance class, represented by its 10% upper bound for filtering; WLP090's older 15% reference is superseded. WLP099's 25% statement is conditional, and its STA1-positive result is recorded; no POF result is inferred. The nullable-spec migration rebuilds only the legacy yeast-spec table transactionally, preserving rows and recipe/log documents. Tests exercise migration twice, retained private work, unknowns, alcohol intervals, medium separation, manual export round trips and search ranking.

### A single Recipe Builder and simpler mobile navigation

The main navigation now has **Recipe Builder**, Ingredient Library, Recipe Book and Brew Log. Builder follows **Water → Beer goals → Malt build → Hops → Yeast → Additives → Recipe summary**. New recipes start with five US gallons (18.927 L) of total mash + sparge water. Equipment, absorption, packaging loss and bottle size are adjustable. **Build malt bill & continue** applies the closest generated recipe; **Generate recipe options** offers three complete alternatives. **Keep current ingredients** preserves all ingredient amounts and timing while retaining the new goals and style. Goal/style edits alone do not change the ingredients.

The builder remembers the current step and each screen's scroll position while browsing the library/book. Ingredient edits stay in browser drafts; goal drafts are stored by recipe ID. Saved JSON and BeerXML BD_* extensions preserve water assumptions and design targets. The summary includes water/yield/bottle estimate, grist percentages, hop stages and doses, yeast pitch needs, additive timing, notes, export and optional sharing. Mobile shows a step selector instead of seven tiny navigation buttons.

The water-aware solver normalizes each candidate to the chosen water budget before calculating gravity and hop utilization. It optimizes at that resulting post-boil volume. Explicit manual grain edits instead use `post-boil L = starting water L − evaporation L − mash grain kg × absorption L/kg`; they never rescale the brewer's entered masses. Invalid budgets keep the last valid recipe and show an error. Scaling an existing recipe recalculates its saved starting-water requirement. Ingredient pickers for malts, hops and yeast are searchable, alphabetical, and offer per-row info buttons. Mouse hover or keyboard arrows preview a choice before selection. Additives have explicit **Boil**, **Whirlpool / hop stand**, and **Steep / dry hop** stages alongside mash, fermentation, conditioning and packaging.
